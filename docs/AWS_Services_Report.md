## 1. บทสรุปสำหรับผู้บริหาร

ระบบนี้คือเว็บแอปพลิเคชันสำหรับ **จัดการคลังสินค้าและพื้นที่จัดเก็บของท่าเรือ (Port Warehouse
Management System)** ที่ให้ตัวแทนขนส่งจองระวางเรือ ระบุประเภทและจำนวนตู้คอนเทนเนอร์
ติดตามสถานะการขนส่ง และให้เจ้าหน้าที่ท่าเรือจัดการบริการ ตารางเรือ สต็อกในคลัง และดูรายงานได้

แต่ **แก่นของโครงงานไม่ใช่ตัวฟีเจอร์ระบบท่าเรือ** — แก่นคือการพิสูจน์ว่าสถาปัตยกรรม
**Multi-Tier บน Cloud** ร่วมกับ **Load Balancing** และ **CI/CD Pipeline**
แก้ปัญหาสามข้อของระบบเดิมได้จริง โดยมีหลักฐานเชิงตัวเลขรองรับ

ผลการทดลองที่ได้จริงจากระบบที่พัฒนาแล้ว:

| การทดลอง | ผลลัพธ์ |
|---|---|
| การกระจายโหลด (120 คำขอ) | กระจาย 50.0% / 50.0% ไปยังเซิร์ฟเวอร์ทั้งสองเครื่อง · ไม่มีคำขอใดล้มเหลว |
| ความทนทานเมื่อเซิร์ฟเวอร์ล่ม (257 คำขอ) | **ความพร้อมใช้งาน 100.00%** · ไม่มีช่วงขาดบริการเลย |
| เทสต์อัตโนมัติของ Backend | ผ่าน 30 จาก 30 รายการ |
| ตรวจความถูกต้องของ Infrastructure as Code | `terraform validate` ผ่าน |

## 2. ปัญหาที่ระบบแก้ และการเชื่อมโยงกับบริการที่เลือก

ทุกบริการที่เลือกต้องตอบปัญหาข้อใดข้อหนึ่งใน 3 ข้อนี้ได้ ถ้าตอบไม่ได้แปลว่าไม่จำเป็น

| # | ปัญหาของระบบเดิม | ผลกระทบ | บริการที่ใช้แก้ |
|---|---|---|---|
| 1 | **เซิร์ฟเวอร์เครื่องเดียวรับผู้ใช้พร้อมกันจำนวนมากไม่ไหว** ผู้ใช้ทั้งเจ้าหน้าที่ ตัวแทนขนส่ง และผู้เกี่ยวข้องเข้าใช้พร้อมกัน | ระบบช้าหรือหยุดให้บริการ | **ALB** + **EC2 หลายเครื่องคนละ AZ** + **Health Check** |
| 2 | **ติดตั้งเวอร์ชันใหม่ด้วยมือทีละเครื่อง** | ช้า เสี่ยงผิดพลาด และแต่ละเครื่องอาจได้เวอร์ชันไม่ตรงกัน | **Docker** + **ECR** + **GitHub Actions** + **SSM** |
| 3 | **ย้อนกลับเวอร์ชันเดิมไม่ทัน** เมื่อเวอร์ชันใหม่มีข้อบกพร่อง | ระบบใช้งานไม่ได้จนกว่าจะแก้เสร็จ | **ECR เก็บ image ทุกเวอร์ชัน** + **workflow rollback** |

## 3. สถาปัตยกรรมโดยรวม

```
ผู้ใช้ (เบราว์เซอร์)  ── คุยกับโดเมนเดียวผ่าน HTTPS ตลอด
   │
   ▼
CloudFront (ทางเข้าเดียวของทั้งระบบ)
   │
   ├── /  และไฟล์เว็บ ──────► S3 (ไฟล์ React, bucket แบบ private)
   │                            เข้าถึงผ่าน Origin Access Control เท่านั้น
   │
   └── /api/*  และ /health ──► Application Load Balancer ── Public Subnet ทั้ง 2 AZ
             │                    ตรวจสุขภาพที่ GET /health ทุก 15 วินาที
             │
             ├──► EC2 เครื่อง A  (Private Subnet · ap-southeast-1a) ─┐  Docker: Node.js + Express
             └──► EC2 เครื่อง B  (Private Subnet · ap-southeast-1b) ─┤
                                                                     │
                                          Amazon RDS MySQL ◄─────────┘
                                          (Private Subnet · ไม่มีเส้นทางออกอินเทอร์เน็ต)

CI/CD:  git push → GitHub Actions → ทดสอบ → docker build → ECR
                                  → SSM Send-Command → deploy ทีละเครื่อง

CloudWatch:  รับ Log และ Metric จากทุกชั้น (ALB · EC2 · RDS) + Alarm แจ้งเตือน
```

### การแบ่งชั้นเครือข่าย

| ชั้น | Subnet | สิ่งที่อยู่ในนั้น | ออกอินเทอร์เน็ตได้ไหม |
|---|---|---|---|
| Presentation | — | S3 + CloudFront (บริการนอก VPC) | ผู้ใช้เข้าถึงได้ผ่าน CloudFront เท่านั้น |
| Load Balancing | Public × 2 AZ | ALB | รับ inbound จากอินเทอร์เน็ต |
| Application | Private-app × 2 AZ | EC2 ที่รัน API | ออกได้ผ่าน NAT (ดึง image, ส่ง log) แต่เข้าจากภายนอกไม่ได้ |
| Database | Private-db × 2 AZ | RDS MySQL | **ไม่มีเส้นทางออกอินเทอร์เน็ตเลย** |

**Security Group ต่อกันเป็นลูกโซ่** ไม่ได้เปิดตามช่วง IP:

```
อินเทอร์เน็ต ─(80, 443)→ [ALB SG] ─(3000)→ [App SG] ─(3306)→ [DB SG]
```

ข้อดีของการอ้างถึง Security Group แทน CIDR คือ ถ้า IP ของ ALB เปลี่ยน (ซึ่งเปลี่ยนได้เอง)
กฎยังถูกต้องอยู่ และไม่มีทางเผลอเปิดกว้างเกินโดยไม่ตั้งใจ

## 4. บริการ AWS ที่ใช้ — รายบริการพร้อมเหตุผล

### 4.1 Amazon VPC — เครือข่ายส่วนตัว

| หัวข้อ | รายละเอียด |
|---|---|
| **ใช้ทำอะไร** | สร้างเครือข่ายส่วนตัว 10.0.0.0/16 แบ่งเป็น 6 subnet (public/app/db × 2 AZ) |
| **ทำไมต้องมี** | ถ้าไม่มี VPC ทุกอย่างจะอยู่บนเครือข่ายสาธารณะ รวมถึงฐานข้อมูล การแบ่ง subnet ทำให้ RDS **ไม่มีเส้นทางออกอินเทอร์เน็ตเลย** แม้จะมีคนได้รหัสผ่านฐานข้อมูลไปก็ต่อจากภายนอกไม่ได้ |
| **การตั้งค่าสำคัญ** | NAT Gateway ให้ EC2 ในชั้น private ออกไปดึง Docker image ได้ · S3 Gateway Endpoint (ไม่คิดเงิน) ลดปริมาณข้อมูลที่วิ่งผ่าน NAT เพราะ ECR เก็บ image layer ไว้ใน S3 |
| **ค่าใช้จ่าย** | VPC เอง subnet route table และ Security Group ไม่คิดเงิน · NAT Gateway คิดรายชั่วโมง + ค่าข้อมูลที่ผ่าน |

### 4.2 Application Load Balancer — หัวใจของโครงงาน

| หัวข้อ | รายละเอียด |
|---|---|
| **ใช้ทำอะไร** | รับคำขอทั้งหมดจากผู้ใช้แล้วกระจายไปยัง EC2 ทั้งสองเครื่อง พร้อมตรวจสุขภาพเครื่องอยู่ตลอด |
| **ทำไมเลือก ALB ไม่ใช่ NLB** | ระบบนี้เป็น HTTP ทั้งหมด ALB ทำงานที่ Layer 7 จึงเข้าใจ path และ header ได้ ทำ path-based routing และ health check ระดับ HTTP ได้ ในขณะที่ NLB ทำงานที่ Layer 4 ตรวจได้แค่ว่าพอร์ตเปิดอยู่ |
| **ทำไมสำคัญที่สุด** | เป็นตัวที่แก้ปัญหาข้อ 1 โดยตรง และเป็นตัวที่ทำให้ deploy ได้โดยไม่มี downtime |

**ค่าที่ตั้งไว้และเหตุผล**

| ค่า | ตั้งเป็น | เหตุผล |
|---|---|---|
| `health_check.path` | `/health` | endpoint นี้ query ฐานข้อมูลจริงก่อนตอบ 200 ไม่ใช่แค่บอกว่า process ยังอยู่ |
| `interval` | 15 วินาที | ไวพอจะจับเครื่องที่ล่มได้ใน ~45 วินาที |
| `healthy_threshold` | 2 | ต้องผ่าน 2 ครั้งติดจึงถือว่าพร้อม กันการรับ traffic ตอนแอปยังเริ่มไม่เสร็จ |
| `unhealthy_threshold` | 3 | ต้องล้มเหลว 3 ครั้งติดจึงถอดออก ไม่ถอดเครื่องที่แค่ช้าชั่วคราว |
| `deregistration_delay` | **30 วินาที** | ตอน deploy ALB หยุดส่งคำขอใหม่แล้วรอ 30 วินาทีให้คำขอที่ค้างอยู่ทำงานจบ ค่านี้เป็นเหตุผลที่แอปต้องรองรับ SIGTERM ถ้าตั้งเป็น 0 ผู้ใช้ที่กำลังกดยืนยันการจองจะถูกตัดกลางคัน (AWS แนะนำ 30–60 วินาทีสำหรับ service ทั่วไป [2]) |
| `stickiness` | **ปิด** | แอปเป็น stateless ทุกเครื่องรับคำขอไหนก็ได้ ถ้าเปิด stickiness จะเป็นการกลบปัญหา session ที่เก็บใน memory แทนที่จะแก้ที่ต้นเหตุ |

### 4.3 Amazon EC2 — เซิร์ฟเวอร์แอปพลิเคชัน

| หัวข้อ | รายละเอียด |
|---|---|
| **ใช้ทำอะไร** | รัน Docker container ของ Backend API จำนวน 2 เครื่อง **คนละ Availability Zone** |
| **ทำไมเลือก EC2** | เห็นกลไกทุกขั้นตอน — เห็นการติดตั้ง เห็นการเชื่อมกับ target group เห็นว่าตอนเครื่องล่มเกิดอะไรขึ้น ตรงกับวัตถุประสงค์การเรียนรู้ |
| **ทำไมต้องคนละ AZ** | ถ้าอยู่ AZ เดียวกัน เมื่อ AZ นั้นล่มระบบดับทั้งหมด การกระจาย 2 AZ ทำให้ระบบทนต่อการล่มของศูนย์ข้อมูลทั้งศูนย์ |
| **ทำไมไม่ใช้ Auto Scaling** | **ตั้งใจกำหนดขอบเขต** ให้จำนวนเครื่องคงที่ เพื่อให้ผลการทดลองอ่านได้ชัดว่าระบบเสถียรเพราะการกระจายโหลด ไม่ใช่เพราะระบบเพิ่มเครื่องให้เอง |

**การรักษาความปลอดภัยของเครื่อง**

- **IMDSv2 บังคับ** (`http_tokens = "required"`) — ป้องกันการโจมตีแบบ SSRF ที่หลอกให้แอปอ่าน credential จาก metadata service
- **ไม่เปิดพอร์ต SSH เลย** — เข้าเครื่องผ่าน SSM Session Manager ซึ่งไม่ต้องมี key ไม่ต้องมี public IP
- **container ไม่ได้รันด้วย root** (`USER node` ใน Dockerfile)
- **สิทธิ์ IAM แคบที่สุด** — อ่าน SSM Parameter ได้เฉพาะ path ของโครงงานนี้ และดึง ECR ได้อย่างเดียว push ไม่ได้

### 4.4 Amazon RDS for MySQL — ฐานข้อมูลกลาง

| หัวข้อ | รายละเอียด |
|---|---|
| **ใช้ทำอะไร** | เก็บข้อมูลทั้งหมด 11 ตาราง (ผู้ใช้ บริการ เที่ยวเรือ การจอง คำสั่งขนส่ง สต็อก ประวัติการทำงาน) |
| **ทำไมต้องเป็นฐานข้อมูลกลาง** | นี่คือสิ่งที่ทำให้แอปเป็น stateless ได้ — **state ทั้งหมดอยู่ที่นี่ที่เดียว** ไม่ว่า ALB จะส่งคำขอไปเครื่องไหน ก็อ่านเขียนข้อมูลชุดเดียวกัน |
| **ทำไม managed ไม่ใช่ MySQL บน EC2** | RDS ทำ backup อัตโนมัติ แพตช์ให้เอง และทำ failover ให้เมื่อเปิด Multi-AZ ถ้าติดตั้งเองต้องดูแลทั้งหมดนี้เอง ซึ่งกินเวลาที่ควรใช้กับส่วนที่เป็นแก่นของโครงงาน |
| **ทำไม MySQL ไม่ใช่ DynamoDB** | ข้อมูลมีความสัมพันธ์ชัดเจน (การจอง → รายการตู้ → ประเภทตู้) และต้องการ transaction ที่รับประกันว่าการหักโควตาระวางเรือกับการสร้างรายการจองสำเร็จหรือล้มเหลวพร้อมกัน — DynamoDB ทำ join ไม่ได้และ transaction จำกัดกว่า |

**การตั้งค่าสำคัญ**

- `publicly_accessible = false` — **ห้ามเปิดเด็ดขาด** ฐานข้อมูลต้องเข้าถึงได้จากใน VPC เท่านั้น
- `storage_encrypted = true` — เข้ารหัสข้อมูลที่เก็บอยู่
- `backup_retention_period = 7` — ย้อนคืนข้อมูลไปจุดใดก็ได้ใน 7 วันย้อนหลัง
- `multi_az` — เป็นตัวแปร ปิดช่วงพัฒนาเพราะคิดเงินเป็นสองเท่า เปิดตอนสาธิต Stage 3 เพื่อแสดง failover
- `slow_query_log` เปิด และตั้ง `long_query_time = 1` — บันทึก query ที่ช้ากว่า 1 วินาที ใช้หาคอขวดตอนทดสอบโหลด

### 4.5 Amazon S3 + Amazon CloudFront — ส่วนหน้าเว็บ

| หัวข้อ | รายละเอียด |
|---|---|
| **ใช้ทำอะไร** | S3 เก็บไฟล์ที่ build จาก React (HTML, JS, CSS) · CloudFront กระจายไฟล์ผ่าน edge location พร้อม HTTPS |
| **ทำไมไม่วางบน EC2** | ไฟล์เว็บเป็น static ไม่ต้องประมวลผล การวางบน S3 ทำให้ไม่กินทรัพยากรของเซิร์ฟเวอร์ที่ต้องรับงาน API และ S3 มีความทนทาน 99.999999999% (11 nines) |
| **ทำไมต้องมี CloudFront** | (1) ให้ HTTPS ฟรีโดยไม่ต้องซื้อใบรับรองและไม่ต้องมีโดเมนของตัวเอง (2) แคชไฟล์ไว้ที่ edge ใกล้ผู้ใช้ ลดเวลาโหลด (3) ทำให้ปิด S3 เป็น private ได้สนิท (4) **เป็นทางเข้าเดียวของทั้งเว็บและ API** ทำให้ทุกอย่างอยู่โดเมนเดียวกัน จึงไม่มีปัญหา mixed content และไม่ต้องตั้ง CORS |

**Origin Access Control (OAC)** — S3 bucket ปิดสาธารณะทั้งหมด (`block_public_acls`,
`restrict_public_buckets` เปิดทุกตัว) CloudFront เข้าถึงผ่าน OAC ซึ่งเป็นวิธีที่ AWS แนะนำ
แทน Origin Access Identity (OAI) แบบเดิม เพราะใช้ credential ระยะสั้นที่หมุนเวียนบ่อย
และรองรับ resource-based policy ที่ละเอียดกว่า [5]

**CloudFront เป็นทางเข้าเดียวของทั้งเว็บและ API**

การออกแบบให้ CloudFront มี origin สองตัว (S3 สำหรับไฟล์เว็บ และ ALB สำหรับ `/api/*`
กับ `/health`) แก้ปัญหาสองข้อพร้อมกัน:

1. **ป้องกัน mixed content** — ถ้าให้เบราว์เซอร์เรียก ALB ตรง ๆ หน้าเว็บที่เสิร์ฟผ่าน HTTPS
   จะเรียกปลายทางที่เป็น HTTP ซึ่งเบราว์เซอร์บล็อกทุกคำขอตามนโยบายความปลอดภัย
   **ระบบจะใช้งานไม่ได้เลย** และการแก้ด้วยการซื้อใบรับรองให้ ALB ต้องมีโดเมนเป็นของตัวเอง
2. **ไม่ต้องตั้ง CORS** — เมื่ออยู่โดเมนเดียวกันก็เป็น same-origin ไม่มีคำขอข้ามโดเมน

`ordered_cache_behavior` ของ `/api/*` ตั้ง cache policy เป็น **CachingDisabled** เพราะข้อมูล
พื้นที่คงเหลือของเที่ยวเรือต้องสดเสมอ และตั้ง origin request policy เป็น
**AllViewerExceptHostHeader** เพื่อส่ง header `Authorization` ต่อไปให้ ALB
ถ้าไม่ส่งต่อ JWT จะหายกลางทางและทุกคำขอจะได้ 401

**ปัญหาเส้นทางของ SPA และวิธีแก้ที่เลือกใช้**

React Router จัดการเส้นทางที่ฝั่งเบราว์เซอร์ แต่ S3 ไม่รู้จัก path อย่าง `/app/bookings`
เพราะไม่มีไฟล์ชื่อนั้นอยู่จริง เมื่อผู้ใช้กด refresh หรือเปิดลิงก์ตรงจะได้ 404

วิธีที่พบบ่อยในบทความทั่วไปคือตั้ง `custom_error_response` ให้ CloudFront เจอ 403/404
แล้วส่ง `index.html` กลับพร้อมสถานะ 200 [6] **แต่วิธีนี้ใช้กับสถาปัตยกรรมนี้ไม่ได้**
เพราะ `custom_error_response` มีผลกับทั้ง distribution ไม่แยกตาม behavior เมื่อ API
อยู่ใต้โดเมนเดียวกัน คำขออย่าง `GET /api/bookings/999` ที่ควรได้ 404 จะถูกแทนที่ด้วย
`index.html` และสถานะ 200 ทำให้การจัดการข้อผิดพลาดทั้งระบบพัง

ระบบนี้จึงแก้ที่ต้นทางด้วย **CloudFront Function** ที่ทำงานตอน viewer-request
และผูกไว้กับ behavior ของไฟล์เว็บเท่านั้น ฟังก์ชันตรวจว่า URI มีนามสกุลไฟล์หรือไม่
ถ้าไม่มีแสดงว่าเป็นเส้นทางของ React Router ให้เขียน URI เป็น `/index.html` ก่อนส่งไป S3
คำขอที่ไปยัง `/api/*` ไม่ผ่านฟังก์ชันนี้ จึงยังคืนสถานะจริงจาก API ได้ถูกต้อง

> **จุดที่ต้องระวังเพิ่ม:** bucket policy ต้องให้สิทธิ์ `s3:ListBucket` ด้วย ไม่ใช่แค่
> `s3:GetObject` เพราะถ้าไม่มี S3 จะตอบ 403 แทน 404 เมื่อไม่พบไฟล์ ทำให้แยกไม่ออกระหว่าง
> "ไม่มีสิทธิ์" กับ "ไม่มีไฟล์" [6]

**นโยบายแคชที่ตั้งไว้ตอน deploy**

| ไฟล์ | Cache-Control | เหตุผล |
|---|---|---|
| `assets/*.js`, `*.css` | `max-age=31536000, immutable` | ชื่อไฟล์มี hash ของเนื้อหาอยู่แล้ว เนื้อหาเปลี่ยน = ชื่อเปลี่ยน จึงแคชได้ยาว 1 ปี |
| `index.html` | `no-cache, no-store, must-revalidate` | **ห้ามแคชเด็ดขาด** ไม่งั้นผู้ใช้จะได้หน้าเก่าที่ชี้ไปยังไฟล์ที่ถูกลบไปแล้ว |

### 4.7 AWS Systems Manager (SSM)

| หัวข้อ | รายละเอียด |
|---|---|
| **ใช้ทำอะไร** | (1) **Parameter Store** เก็บรหัสผ่านฐานข้อมูลและ JWT secret แบบเข้ารหัส (2) **Send-Command** ให้ GitHub Actions สั่ง deploy บน EC2 (3) **Session Manager** เข้าเครื่องแก้ปัญหาโดยไม่ต้อง SSH |
| **ทำไมใช้ SSM แทน SSH** | EC2 อยู่ใน private subnet ไม่มี public IP อยู่แล้ว ถ้าจะ SSH ต้องมี bastion host เพิ่ม (ซึ่งคิดเงินและเป็นช่องโจมตีเพิ่ม) และต้องเก็บ private key เป็น GitHub Secret ซึ่งถ้ารั่วคือเข้าเครื่องได้เลย |
| **ทำไมความลับต้องอยู่ใน Parameter Store** | user-data ของ EC2 **อ่านได้จาก EC2 Console** ใครที่เข้า console ได้จะเห็นทุกอย่างในนั้น จึงห้ามใส่รหัสผ่านลงไปตรง ๆ วิธีที่ใช้คือ user-data เก็บแค่ "ชื่อ parameter" แล้วเครื่องดึงค่าจริงเองตอน boot ผ่าน IAM role |

### 4.8 Amazon CloudWatch — การเฝ้าระวัง

| หัวข้อ | รายละเอียด |
|---|---|
| **ใช้ทำอะไร** | รวบรวม Log จาก container (ผ่าน `awslogs` driver) และ Metric จาก ALB, EC2, RDS ไว้ที่เดียว พร้อม Alarm และ Dashboard |
| **ทำไมสำคัญกับโครงงาน** | มี EC2 2 เครื่องส่ง log คนละที่ ถ้าไม่รวมไว้ที่เดียวจะหาต้นเหตุปัญหาไม่ได้ · และ Metric ของ ALB คือแหล่งข้อมูลหลักที่ใช้ทำกราฟประกอบผลการทดลอง Stage 3 |

**Alarm ที่ตั้งไว้ — ตั้งเฉพาะสิ่งที่ต้องมีคนลุกมาดูจริง**

| Alarm | เงื่อนไข | ทำไมสำคัญ |
|---|---|---|
| `unhealthy-hosts` | UnHealthyHostCount > 0 นาน 2 นาที | **สำคัญที่สุด** — ถ้าเหลือเครื่องเดียว ระบบยังทำงานได้แต่ไม่มี HA แล้ว ต้องรีบแก้ก่อนเครื่องที่สองล่ม |
| `alb-5xx` | error 5xx > 10 ครั้งใน 5 นาที | แอปมีปัญหา ไม่ใช่แค่ผู้ใช้กรอกผิด |
| `alb-latency` | เวลาตอบสนอง p99 > 2 วินาที | ใช้ p99 ไม่ใช่ค่าเฉลี่ย เพราะค่าเฉลี่ยกลบผู้ใช้ที่เจอปัญหาจริง |
| `rds-cpu` | CPU > 80% นาน 10 นาที | ฐานข้อมูลเป็นคอขวดที่ scale ยากที่สุด |
| `rds-storage` | พื้นที่ว่าง < 2 GB | ฐานข้อมูลเต็ม = เขียนไม่ได้ = ระบบใช้งานไม่ได้ |

### 4.9 GitHub Actions (บริการภายนอก) — CI/CD

| หัวข้อ | รายละเอียด |
|---|---|
| **ใช้ทำอะไร** | รันเทสต์อัตโนมัติ · build Docker image · push ขึ้น ECR · deploy ทีละเครื่อง · rollback |
| **ทำไมเลือก ไม่ใช่ Jenkins** | Jenkins ต้องมีเซิร์ฟเวอร์ CI เป็นของตัวเอง ซึ่งกลายเป็นอีกเครื่องที่ต้องดูแล ตั้งค่า และคิดเงิน · GitHub Actions ผูกกับ repository อยู่แล้วและ**ใช้ฟรีไม่จำกัดสำหรับ public repository** [7] |
| **ทำไมไม่ใช้ AWS CodePipeline** | ผูกกับ AWS แน่นเกินไป และตั้งค่าซับซ้อนกว่าสำหรับกรณีใช้งานง่าย ๆ แบบนี้ |

**ความปลอดภัยของการเชื่อมต่อ: ใช้ OIDC ไม่ใช่ Access Key**

Workflow ขอ token จาก GitHub แล้วแลกเป็น credential ชั่วคราวของ AWS
(`permissions: id-token: write` + `aws-actions/configure-aws-credentials`)
ข้อดีคือ **ไม่มี AWS Access Key ที่ไม่มีวันหมดอายุเก็บอยู่ใน GitHub Secrets**
ถ้า secret รั่ว ผู้ที่ได้ไปก็ใช้ไม่ได้เพราะ credential มีอายุแค่ระยะสั้นและผูกกับ repository นี้เท่านั้น

| **สร้างการจอง** | ขั้นตอน 3 ขั้นชัดเจน (เลือกเที่ยวเรือ → ระบุตู้และสินค้า → ตรวจทาน) | ฟอร์มยาวหน้าเดียวทำให้ผู้ใช้ละทิ้งกลางทาง |
| | **แถบสรุปพื้นที่คงเหลือที่อัปเดตทันทีตามจำนวนตู้ที่เลือก** | ผู้ใช้เห็นก่อนกดว่าจะเกินโควตาหรือไม่ ไม่ต้องรอ error จากเซิร์ฟเวอร์ |
| | ปุ่ม "ตรวจทาน" ถูกปิดเมื่อข้อมูลยังไม่ครบหรือเกินโควตา | ป้องกันการส่งข้อมูลที่รู้อยู่แล้วว่าจะถูกปฏิเสธ |
| **รายละเอียดการจอง** | **เส้นเวลาสถานะขนส่ง 5 ขั้น** (สร้างคำสั่ง → ตู้เข้าประตูท่า → ขึ้นเรือ → เรือออกจากท่า → ถึงปลายทาง) | สิ่งที่ลูกค้าอยากรู้หลังจองแล้วคือ "ตู้ของฉันอยู่ขั้นไหน" ไม่ใช่แค่ว่ามีรายการจองอยู่ |
| | ปุ่มยืนยันแสดงเฉพาะตอนสถานะ "รอยืนยัน" พร้อมบอกกำหนดปิดรับ | ตาม UC-6 Precondition |
| | **กล่องยืนยันก่อนยกเลิก** ที่บอกผลกระทบชัดเจน (คืนพื้นที่กี่ TEU และกู้คืนไม่ได้) | การยกเลิกเป็นการกระทำที่ย้อนกลับไม่ได้ |
| **ภาพรวม (Dashboard)** | เน้น **รายการที่รอการยืนยัน** ไว้บนสุดพร้อมนับถอยหลังกำหนดปิดรับ | ตอบคำถาม "มีอะไรที่ฉันต้องทำต่อ" ก่อนอย่างอื่น |

### 6.3 ฟีเจอร์ฝั่งผู้ดูแลระบบ (Admin / Port Staff)

| หน้า | ฟีเจอร์ที่ต้องมี | เหตุผล |
|---|---|---|
| **ภาพรวมระบบ** | ตัวชี้วัด 4 ตัว (จำนวนการจอง · รายได้ · การใช้พื้นที่เฉลี่ย · สินค้าต่ำกว่าจุดสั่งซื้อ) + กราฟแนวโน้ม | ผู้ดูแลต้องเห็นสถานะรวมของท่าเรือภายในหน้าจอเดียว |
| | **แถบการใช้พื้นที่ของทุกเที่ยวเรือที่เปิดจอง** เรียงจากที่แน่นที่สุด | บอกว่าเที่ยวไหนใกล้เต็มและควรเปิดเที่ยวเสริม |
| **จัดการการจอง** | ค้นหาข้ามเลขที่จอง ชื่อลูกค้า บริษัท และเลขเที่ยวเรือ | เจ้าหน้าที่รับสายลูกค้าที่บอกข้อมูลมาไม่เหมือนกันทุกครั้ง |
| | **จำกัดการเปลี่ยนสถานะตามลำดับที่อนุญาต** (ไม่ให้ข้ามจาก "รอยืนยัน" ไป "เสร็จสิ้น" โดยตรง) | ป้องกันการข้ามขั้นที่ทำให้ไม่มีการสร้างคำสั่งขนส่ง |
| | อัปเดตสถานะการขนส่งพร้อมบันทึกเวลาอัตโนมัติ | เวลาเหล่านี้เป็นแหล่งข้อมูลของ dwell time ในรายงาน |
| **จัดการบริการและตารางเรือ** | CRUD + **ห้ามลบสิ่งที่ยังถูกอ้างถึงอยู่** และแนะนำให้ปิดใช้งานแทน | ตาม UC-11 Alternate Flow 3 · การลบข้อมูลที่มีธุรกรรมผูกอยู่ทำให้ประวัติเสียหาย |
| | **ห้ามลดความจุเที่ยวเรือต่ำกว่าจำนวนที่จองไปแล้ว** | ไม่งั้น `booked_teu` จะเกิน `capacity_teu` ทันทีซึ่งเป็นสถานะที่เป็นไปไม่ได้ |
| **จัดการประเภทตู้** | CRUD + แสดงจำนวนครั้งที่ถูกใช้ในการจอง | ผู้ดูแลเห็นก่อนกดลบว่าประเภทนี้ถูกใช้อยู่หรือไม่ |
| **จัดการสต็อก** | **แถบเตือนสินค้าต่ำกว่าจุดสั่งซื้อบนสุดของหน้า** | ระดับสต็อกเป็น KPI มาตรฐานของ WMS ที่ต้องเห็นทันที [4] |
| | ปรับสต็อกแยกเป็น 3 ประเภท (รับเข้า / ตัดออก / ปรับตามการตรวจนับ) พร้อมช่องเหตุผล | ตัวเลขคงเหลือต้องอธิบายได้ด้วยประวัติการเคลื่อนไหวเสมอ |
| | **แสดงประวัติการเคลื่อนไหวในกล่องเดียวกับที่กำลังปรับ** | ผู้ดูแลเห็นบริบทก่อนตัดสินใจปรับ ไม่ต้องเปิดหน้าอื่น |
| | ห้ามตัดสต็อกจนติดลบ | จำนวนของจริงติดลบไม่ได้ |
| **รายงาน** | เลือกช่วงวันที่ + กราฟ 3 แบบ (แนวโน้มการจอง · บริการยอดนิยม · สินค้าตามโซน) | ตาม UC-15 |
| | **ส่งออก CSV พร้อม BOM** | ไม่มี BOM แล้วเปิดใน Excel บน Windows ภาษาไทยจะเป็นตัวอักษรผิดเพี้ยน |
| **จัดการผู้ใช้** | CRUD + กำหนดสิทธิ์ + ระงับบัญชี | ตาม UC-10 |
| | **ห้ามผู้ดูแลลดสิทธิ์หรือระงับบัญชีตัวเอง** | ป้องกันการล็อกตัวเองออกจากระบบจนไม่มีใครเข้าไปแก้ได้ |
| | ห้ามลบผู้ใช้ที่มีรายการจองผูกอยู่ แนะนำให้ระงับบัญชีแทน | รักษาประวัติธุรกรรม |

## 7. ฟีเจอร์ที่ควรปรับเพิ่มจาก Use-Case เดิม โดยอ้างอิงระบบจริงในอุตสาหกรรม

จากการศึกษาระบบ **Vehicle Booking System (VBS)** ที่ท่าเรือขนาดใหญ่ใช้จริง เช่น
DP World Southampton, DP World London Gateway และ 1-Stop [1] ร่วมกับแนวปฏิบัติของ
**Warehouse Management System (WMS)** ปัจจุบัน [3][4] พบว่า Use-Case Specification เดิม
ครอบคลุมโครงสร้างพื้นฐานครบแล้ว แต่ยังขาดกลไกบางอย่างที่ทำให้ระบบทำงานได้จริง
ต่อไปนี้คือสิ่งที่เพิ่มเข้าไปพร้อมเหตุผล

### 7.1 โควตาพื้นที่ระวางต่อเที่ยวเรือ (Slot Capacity / TEU Quota) — สำคัญที่สุด

**เพิ่มที่:** ตาราง `vessel_schedules` เพิ่มคอลัมน์ `capacity_teu` และ `booked_teu`
· ตรวจสอบใน UC-5 ก่อนสร้างการจอง

**เหตุผล**

VBS ของท่าเรือจริงทำงานบนหลักการ "จำนวนช่วงเวลาที่เปิดให้จองมีจำกัด" — ระบบกำหนดโควตา
รถบรรทุกต่อวันเพื่อลดความแออัดหน้าประตูท่า และผู้ประกอบการต้องจองช่วงเวลาล่วงหน้า
โดยทั่วไป 24 ชั่วโมงขึ้นไป [1]

ในทางเทคนิค นี่คือสิ่งที่ทำให้ **UC-5 Alternate Flow 1 ("ระบบไม่สามารถรองรับการจองได้")
มีเงื่อนไขจริงให้ตรวจสอบ** ถ้าไม่มีโควตา กิ่งนี้ใน Use-Case Specification จะไม่มีวันเกิดขึ้น
ซึ่งเท่ากับเขียน exception flow ที่ไม่มีความหมาย

**ผลที่ได้ในระบบ:** เมื่อขอจอง 11 TEU บนเที่ยวเรือที่เหลือ 10 TEU ระบบตอบ HTTP 409
พร้อมรายละเอียด `{"requestedTeu": 11, "availableTeu": 10, "capacityTeu": 700}`
ทำให้หน้าเว็บบอกผู้ใช้ได้ตรงจุดว่าเหลือเท่าไหร่ ไม่ใช่แค่ "จองไม่ได้"

### 7.2 เส้นเวลาสถานะการขนส่ง (Shipment Status Timeline)

**เพิ่มที่:** ตาราง `shipment_orders` มี 5 สถานะพร้อมคอลัมน์เวลาแยกแต่ละขั้น
· หน้ารายละเอียดการจองแสดงเป็นเส้นเวลา

**เหตุผล**

VBS ที่ใช้จริงให้ข้อมูล **สถานะแบบเรียลไทม์** ของความพร้อมของตู้และช่วงเวลาที่จองไว้ [1]
Use-Case Specification เดิมระบุใน UC-6 ว่า "ระบบสร้างหรืออัปเดตข้อมูล Shipment Order"
แต่ไม่ได้ระบุว่าลูกค้าจะเห็นความคืบหน้าอย่างไร ซึ่งเป็นสิ่งที่ลูกค้าต้องการที่สุดหลังจองเสร็จ

**ผลพลอยได้ที่สำคัญ:** เวลาที่บันทึกในแต่ละขั้น (`gate_in_at`, `loaded_at`) กลายเป็น
แหล่งข้อมูลของ dwell time ในหัวข้อถัดไปโดยไม่ต้องเก็บข้อมูลเพิ่ม

### 7.3 ตัวชี้วัดระยะเวลาตู้อยู่ในเขตท่า (Dwell Time)

**เพิ่มที่:** หน้ารายงานและภาพรวมระบบ คำนวณจาก
`AVG(TIMESTAMPDIFF(MINUTE, gate_in_at, loaded_at))`

**เหตุผล**

Dwell time เป็น KPI มาตรฐานของ WMS ที่วัดว่าใช้เวลานานเท่าไรกว่ารถจะเข้าและออกจากพื้นที่
และการที่ค่านี้สูงผิดปกติเป็นสัญญาณบอกจุดคอขวดที่ทำให้เกิดค่าปรับ [4]

Use-Case Specification เดิมระบุรายงานไว้เพียง "ยอดขายรายวัน/รายเดือน, สินค้าขายดี,
สินค้าคงคลัง" ซึ่งเป็นมุมมองเชิงการค้า แต่ไม่มีมุมมอง **เชิงปฏิบัติการ** ที่บอกว่า
การดำเนินงานของท่าเรือมีประสิทธิภาพหรือไม่ ซึ่งเป็นเรื่องที่ระบบ WMS มีไว้เพื่อการนี้โดยตรง

### 7.4 โซนจัดเก็บและจุดสั่งซื้อในคลังสินค้า

**เพิ่มที่:** ตาราง `stock_items` เพิ่ม `warehouse_zone` และ `reorder_level`
· หน้าจัดการสต็อกมีตัวกรอง "เฉพาะที่ต่ำกว่าจุดสั่งซื้อ" และแถบเตือนบนสุด

**เหตุผล**

ฟีเจอร์การจัดการลานและท่าเทียบของ WMS ทำหน้าที่ติดตามรถที่เข้าและออก จัดตารางการใช้ท่าเทียบ
และประสานพื้นที่พักสินค้า เพื่อให้การดำเนินงานทั้งหมดทำงานเป็นระบบเดียวกัน [3]
ส่วนการเฝ้าระดับสต็อกเป็นองค์ประกอบสำคัญที่สุดอย่างหนึ่งของ Warehouse KPI Dashboard
ซึ่งให้ความชัดเจนแบบเรียลไทม์เพื่อรักษาระดับสินค้าให้เหมาะสมและลดความเสี่ยงของการขาดสต็อก [4]

Use-Case Specification เดิมมี UC-14 Manage Stock ที่ปรับจำนวนได้ แต่ไม่มีกลไกบอกว่า
**เมื่อไหร่ควรสั่งเพิ่ม** ซึ่งทำให้ระบบเป็นเพียงที่บันทึกตัวเลข ไม่ได้ช่วยตัดสินใจ

### 7.5 บันทึกประวัติการดำเนินการ (Audit Log)

**เพิ่มที่:** ตาราง `audit_logs` บันทึกทุก mutation ของผู้ดูแลระบบ

**เหตุผล**

UC-10, UC-13 และ UC-14 อนุญาตให้ผู้ดูแลระบบแก้ไขข้อมูลของผู้อื่น เปลี่ยนสถานะการจอง
และปรับจำนวนสินค้า การกระทำเหล่านี้กระทบทั้งเงินและของจริง จึงต้องสาวกลับได้ว่าใครทำอะไร
เมื่อไหร่ — โดยเฉพาะเมื่อมีผู้ดูแลระบบหลายคนอย่างในกรณีของท่าเรือ

Use-Case Specification เดิมไม่ได้ระบุเรื่องนี้ไว้ ซึ่งเป็นช่องว่างที่พบบ่อยในระบบที่มีหลายบทบาท

### 7.6 การจองหลายประเภทตู้ในรายการเดียว

**เพิ่มที่:** ตาราง `booking_items` แยกจาก `bookings`

**เหตุผล**

ในทางปฏิบัติ ผู้ส่งออกรายหนึ่งอาจส่งสินค้าที่ต้องใช้ตู้ 20GP จำนวน 2 ตู้ ร่วมกับตู้ 40HC
อีก 1 ตู้ ในการขนส่งครั้งเดียวกัน ถ้าออกแบบให้ 1 การจองมีตู้ได้ประเภทเดียว
ผู้ใช้ต้องสร้าง 2 รายการจองสำหรับการขนส่งชุดเดียว ซึ่งทำให้ติดตามสถานะแยกกันโดยไม่จำเป็น

## 8. การออกแบบเชิงเทคนิคที่สำคัญ

### 8.1 ระบบไร้สถานะ (Stateless) — คำถามที่ถูกถามบ่อยที่สุด

**คำถาม:** มี EC2 สองเครื่องหลัง Load Balancer แล้ว session เก็บที่ไหน

**คำตอบ:** ไม่เก็บที่ไหนเลย ระบบนี้ไม่มี session store

| สิ่งที่ต้องเก็บ | เก็บที่ไหน | ทำไม |
|---|---|---|
| **การยืนยันตัวตน** | **JWT** เซ็นด้วย secret ที่ทั้งสองเครื่องใช้ร่วมกัน | เครื่องไหนก็ตรวจสอบ token เดียวกันได้เอง โดยไม่ต้องคุยกับเครื่องอื่นและไม่ต้องใช้ sticky session |
| **"ตะกร้า" ก่อนยืนยัน** | **แถวใน RDS ที่ `status = 'pending'`** | เป็นข้อมูลถาวรที่ผู้ดูแลระบบเห็นได้ใน UC-13 ด้วย และตรงกับ UC-5 → UC-6 พอดี ไม่ต้องประดิษฐ์แนวคิด cart ขึ้นมาแยกต่างหาก |

**หลักฐานว่าเป็น stateless จริง:** ในการทดสอบ ผู้ใช้เข้าสู่ระบบผ่านเครื่องหนึ่ง
แล้วสร้างและยืนยันการจองซึ่งอาจถูกส่งไปอีกเครื่อง ทุกขั้นทำงานได้ปกติ
และเมื่อปิดเซิร์ฟเวอร์เครื่องหนึ่งกลางการทดสอบ **ไม่มีคำขอใดล้มเหลวเลย**

### 8.2 การป้องกันการจองซ้อนเมื่อมีหลายเครื่อง

ปัญหาที่มองไม่เห็นตอนรันเครื่องเดียว แต่โผล่ทันทีเมื่ออยู่หลัง Load Balancer:
ถ้าลูกค้าสองรายจองที่ว่างสุดท้ายพร้อมกันโดยไปคนละเครื่อง ทั้งคู่จะอ่านค่า `booked_teu`
เดิมแล้วจองผ่านทั้งคู่ ทำให้เที่ยวเรือรับตู้เกินความจุ

**วิธีแก้:** ล็อกแถวเที่ยวเรือด้วย `SELECT ... FOR UPDATE` ภายใน transaction เดียวกับ
การเขียนรายการจองและการบวก `booked_teu`

```sql
START TRANSACTION;
SELECT * FROM vessel_schedules WHERE id = ? FOR UPDATE;  -- ล็อกแถวนี้ไว้
-- ตรวจโควตา สร้าง booking สร้าง booking_items บวก booked_teu
COMMIT;
```

เครื่องที่สองจะรอจนเครื่องแรกทำเสร็จ แล้วอ่านค่าที่อัปเดตแล้วจึงตรวจโควตาได้ถูกต้อง
มีเทสต์อัตโนมัติครอบกรณีนี้ไว้

### 8.3 Health Check สองระดับ

AWS แนะนำให้พิจารณาว่า health check ควรตื้นหรือลึกแค่ไหน เพราะการตรวจที่ลึกเกินไป
อาจทำให้ระบบถอดเครื่องออกทั้งหมดเมื่อ dependency ล้มชั่วคราว [2]

| Endpoint | ใครใช้ | ตรวจอะไร | เหตุผล |
|---|---|---|---|
| `GET /health/live` | Docker healthcheck | process ยังอยู่ไหม ไม่แตะฐานข้อมูล | ใช้ตัดสินว่าควรรีสตาร์ท container หรือไม่ |
| `GET /health` | **ALB target group** | `SELECT 1` กับฐานข้อมูลจริง | ถ้าเครื่องยังตอบ HTTP ได้แต่ต่อฐานข้อมูลไม่ได้ เครื่องนั้นให้บริการจริงไม่ได้ ต้องถูกถอดออกจาก target group |

`GET /health` คืนข้อมูลที่ใช้เป็นหลักฐานการทดลองโดยตรง:

```json
{
  "status": "ok",
  "instance": { "hostname": "ip-10-0-11-23", "availabilityZone": "ap-southeast-1a", "instanceId": "i-0abc" },
  "version": { "gitSha": "a1b2c3d", "imageTag": "a1b2c3d" },
  "db":       { "ok": true, "latencyMs": 3 },
  "uptimeSec": 842
}
```

### 8.4 การปิดระบบอย่างนุ่มนวล (Graceful Shutdown)

ลำดับที่เกิดขึ้นจริงตอน deploy เครื่อง A:

```
1. ALB เริ่มถอดเครื่อง A ออก → เข้าโหมด draining (รอ 30 วินาทีตาม deregistration_delay)
2. docker stop ส่งสัญญาณ SIGTERM ให้ process
3. แอปหยุดรับ connection ใหม่ แต่ปล่อยให้คำขอที่ค้างอยู่ทำงานจนจบ
4. ปิด connection pool ของฐานข้อมูล แล้วจึงออกจาก process
```

**ถ้าข้ามขั้นที่ 3** ผู้ใช้ที่กำลังกดยืนยันการจองอยู่จะเจอ HTTP 502 กลางคัน
ซึ่งเป็นบั๊กที่ไม่ปรากฏตอนทดสอบบนเครื่องตัวเองแต่เกิดทุกครั้งที่ deploy จริง

**รายละเอียดที่มองข้ามกันบ่อย:** Dockerfile ใช้ `tini` เป็น PID 1 เพราะถ้าให้ `node`
เป็น PID 1 เอง มันจะไม่ได้รับสัญญาณ SIGTERM ตามมาตรฐาน Linux ทำให้ graceful shutdown
ที่เขียนไว้ไม่ทำงานเลย

### 8.5 การ deploy แบบไม่มีเวลาหยุดให้บริการ

Workflow deploy ไล่ทีละเครื่อง และ**รอจนเครื่องนั้นกลับมา healthy ในสายตาของ ALB จริง ๆ**
ก่อนไปเครื่องถัดไป (ตรวจ `describe-target-health` ทุก 5 วินาที สูงสุด 40 ครั้ง)
ระหว่างที่เครื่อง A กำลังอัปเดต เครื่อง B ยังรับผู้ใช้อยู่ จึงไม่มีช่วงที่ระบบไม่มีเครื่องให้บริการ

หลัง deploy เสร็จมีขั้นตรวจสอบที่ยิงผ่าน ALB 10 ครั้งแล้วเทียบว่า `gitSha` ที่ได้ตรงกับ
เวอร์ชันที่เพิ่ง deploy ทุกครั้ง — ถ้ามีเครื่องใดยังรันเวอร์ชันเก่าอยู่ workflow จะล้มเหลว
ไม่ปล่อยผ่านไปเงียบ ๆ

### 8.6 กลไก Rollback

```
เกิดปัญหาหลัง deploy
  → เปิด GitHub Actions เลือก workflow "Rollback"
  → ใส่แท็ก git SHA ของเวอร์ชันที่ดีก่อนหน้า + เหตุผล
  → ระบบตรวจก่อนว่ามี image แท็กนั้นอยู่ใน ECR จริง (กันพิมพ์ผิดแล้วระบบล่มหนักกว่าเดิม)
  → SSM สั่งทุกเครื่องดึง image แท็กนั้นมารัน ทีละเครื่องเหมือนตอน deploy
  → ตรวจยืนยันผ่าน ALB ว่าทุกเครื่องรันเวอร์ชันที่ต้องการแล้ว
```

**เร็วกว่า deploy ปกติมากเพราะไม่ต้อง build ใหม่** — image ของเวอร์ชันเก่ายังอยู่ใน ECR
แล้ว การ rollback จึงใช้เวลาเท่ากับเวลาดึง image และรีสตาร์ท container เท่านั้น

| 1 | Frontend ถูก build ให้เรียก API ที่ `http://<alb>` ขณะที่หน้าเว็บเสิร์ฟผ่าน HTTPS จาก CloudFront | เบราว์เซอร์บล็อกทุกคำขอด้วยกฎ mixed content — **ระบบใช้ไม่ได้เลยบน AWS** แต่บนเครื่องตัวเองไม่พบปัญหาเพราะเป็น HTTP ทั้งคู่ | ให้ CloudFront เป็นทางเข้าเดียว เพิ่ม ALB เป็น origin ที่สองสำหรับ `/api/*` และ `/health` · frontend เรียก API ด้วย path สัมพัทธ์ · ผลพลอยได้คือไม่ต้องตั้ง CORS อีกต่อไป |
| 2 | `user-data.sh` สั่ง `dnf install -y awscli` ซึ่งไม่มีแพ็กเกจชื่อนี้ใน Amazon Linux 2023 | คำสั่งล้มเหลว แล้ว `set -e` หยุดสคริปต์ทั้งไฟล์ → **EC2 boot ขึ้นมาโดยไม่มีแอปเลย** | ตัดออก (AWS CLI v2 ติดตั้งมาให้แล้ว) · เพิ่มการตรวจว่าคำสั่งที่จำเป็นใช้ได้จริงก่อนไปต่อ · ทำให้การติดตั้ง CloudWatch agent ไม่ทำให้ทั้งสคริปต์ล้มเหลว |
| 3 | ใช้ `custom_error_response` แปลง 403/404 เป็น `index.html` ตามวิธีที่พบทั่วไป | เมื่อ API อยู่โดเมนเดียวกัน คำขอที่ควรได้ 404 จะได้ `index.html` + 200 → การจัดการข้อผิดพลาดทั้งระบบพัง | เปลี่ยนไปใช้ CloudFront Function ที่ผูกกับ behavior ของไฟล์เว็บเท่านั้น |
| 4 | หน้าค้นหากรองประเภทบริการที่ฝั่งเบราว์เซอร์หลังดึงข้อมูลมาแล้ว | กรองได้เฉพาะรายการในหน้าปัจจุบัน และตัวเลข "พบกี่รายการ" ไม่ตรงความจริง | ย้ายไปกรองที่ฐานข้อมูลด้วยพารามิเตอร์ `serviceType` |
| 5 | แถบเมนูด้านข้างใช้คลาส `lg:top-dvh` ที่ไม่มีอยู่จริง และ `mt-auto` ไม่ทำงานเพราะ container ไม่ใช่ flex column | ส่วนออกจากระบบไม่ไปติดขอบล่างตามที่ออกแบบ | ตั้ง `flex flex-col` + `lg:h-dvh lg:sticky lg:top-0` ให้ถูกต้อง |

**บทเรียน:** ข้อ 1 และ 2 เป็นข้อบกพร่องประเภทที่ **ทดสอบบนเครื่องตัวเองไม่มีวันเจอ**
เพราะเกิดจากความต่างระหว่างสภาพแวดล้อมพัฒนากับสภาพแวดล้อมจริง (HTTP กับ HTTPS
และระบบปฏิบัติการที่ต่างกัน) นี่คือเหตุผลที่ CI ต้องมีขั้น `terraform validate`
และเหตุผลที่ควรทดลอง deploy จริงให้เร็วที่สุดแทนที่จะรอจนใกล้กำหนดส่ง

**การตรวจทานรอบที่สอง** พบอีก 6 จุด ซึ่งส่วนใหญ่เป็นผลจากการที่ระบบมีเซิร์ฟเวอร์

| # | ข้อบกพร่อง | ผลกระทบ | การแก้ไข |
|---|---|---|---|

| 9 | เมื่อ API ตอบ 401 ระบบล้าง token ทิ้งแต่ไม่ได้แจ้งสถานะผู้ใช้ในแอป | ผู้ใช้ค้างอยู่หน้าเดิม เห็นแต่ข้อความผิดพลาด โดยไม่รู้ว่าเซสชันหมดอายุและต้องเข้าสู่ระบบใหม่ | ส่ง event ของเบราว์เซอร์เมื่อเจอ 401 แล้วให้ตัวจัดการสถานะผู้ใช้ล้างค่า ระบบจะพาไปหน้าเข้าสู่ระบบเอง |
| 10 | หน้าภาพรวมของลูกค้ากลืนข้อผิดพลาดด้วย `.catch(() => undefined)` | "โหลดข้อมูลไม่สำเร็จ" แสดงผลเหมือน "ยังไม่มีรายการจอง" ผู้ใช้เข้าใจผิดว่าข้อมูลหายไป | แสดงข้อความผิดพลาดพร้อมปุ่มลองใหม่ |
| 11 | ส่ง `items` ที่มีประเภทตู้ซ้ำกัน ระบบตอบว่า "มีประเภทตู้ที่เลือกไม่ถูกต้อง" | ข้อความบอกเหตุผลผิด ทำให้ผู้เรียกใช้ API แก้ปัญหาผิดจุด | รวมจำนวนของตู้ประเภทเดียวกันก่อนคำนวณ · เพิ่มเทสต์ครอบกรณีนี้ |

> การทดลองรัน migration พร้อมกันสองกระบวนการ (ทั้งแบบมีและไม่มีล็อก รวมถึงแบบถ่างช่องเวลา)

## 11. ข้อจำกัดของระบบ

การระบุข้อจำกัดอย่างตรงไปตรงมาแสดงว่าเข้าใจระบบที่ออกแบบเอง ไม่ใช่จุดอ่อนของรายงาน

| ข้อจำกัด | ผลกระทบ | ทางแก้ถ้าจะพัฒนาต่อ |
|---|---|---|
| **ถ้า EC2 ล่มทั้งสองเครื่อง ระบบหยุดให้บริการ** | ไม่มีเครื่องสำรองอัตโนมัติ | เพิ่ม Auto Scaling Group ที่ตั้ง minimum เป็น 2 เพื่อให้ระบบสร้างเครื่องทดแทนอัตโนมัติ (อยู่นอกขอบเขตโครงงานโดยตั้งใจ) |
| **จำนวนเครื่องคงที่ ไม่รองรับโหลดพุ่งสูงเกินความจุที่ตั้งไว้** | ถ้ามีผู้ใช้มากกว่าที่ 2 เครื่องรับไหว ระบบจะช้า | Auto Scaling ตาม CPU หรือจำนวนคำขอต่อ target |
| **RDS เป็นจุดเดียวที่ล้มแล้วระบบล้มตาม** (ตอน Single-AZ) | ฐานข้อมูลล่ม = ระบบใช้งานไม่ได้ทั้งหมด | เปิด Multi-AZ (ทำได้แล้วผ่านตัวแปร) และเพิ่ม Read Replica สำหรับงานอ่านหนักเช่นรายงาน |
| **NAT Gateway มีตัวเดียว** | ถ้า AZ ที่มี NAT ล่ม EC2 ในอีก AZ จะออกอินเทอร์เน็ตไม่ได้ (แต่ยังให้บริการผู้ใช้ได้ปกติ) | สร้าง NAT หนึ่งตัวต่อ AZ |
| **การรับส่งระหว่าง CloudFront กับ ALB ยังเป็น HTTP** | ผู้ใช้กับ CloudFront เข้ารหัสด้วย HTTPS แล้ว แต่ช่วง CloudFront ไป ALB ยังไม่เข้ารหัส (อยู่ในเครือข่ายของ AWS) | ขอใบรับรองจาก ACM (ฟรี) แล้วเพิ่ม listener :443 ที่ ALB และเปลี่ยน `origin_protocol_policy` เป็น `https-only` · โค้ด Terraform เตรียมไว้แล้วในคอมเมนต์ |
| **ไม่มีระบบชำระเงินจริง** | บันทึกได้แค่ราคาประมาณการ | เชื่อมกับ payment gateway ซึ่งอยู่นอกขอบเขตของโครงงานด้าน Cloud |
| **การทดสอบโหลดยังเป็นสเกลเล็ก** | ยังไม่ทราบขีดจำกัดจริงของระบบ | ใช้เครื่องมืออย่าง k6 หรือ Apache JMeter ยิงระดับพันคำขอต่อวินาที |
| **ไม่มี Redis หรือ ElastiCache** | ทุกคำขอไปถึงฐานข้อมูล | เพิ่ม ElastiCache สำหรับแคชผลรายงานที่คำนวณหนักและเปลี่ยนไม่บ่อย |

## 12. คำถามที่คาดว่าจะถูกถามและคำตอบ

| คำถาม | คำตอบ |
|---|---|
| **Session เก็บที่ไหน** | ไม่เก็บที่ไหนเลย ใช้ JWT ที่เซ็นด้วย secret ร่วมกันทั้งสองเครื่อง ส่วน "ตะกร้า" คือแถวในฐานข้อมูลที่สถานะ `pending` — พิสูจน์แล้วด้วยการปิดเซิร์ฟเวอร์เครื่องหนึ่งระหว่างใช้งานแล้วไม่มีคำขอใดล้มเหลว |
| **ทำไมไม่ใช้ Auto Scaling** | ตั้งใจกำหนดขอบเขตให้จำนวนเครื่องคงที่ เพื่อให้ผลการทดลองอ่านได้ชัดว่าระบบเสถียรเพราะ Load Balancing ไม่ใช่เพราะระบบเพิ่มเครื่องให้เอง — ถ้าใส่จะแยกสองปัจจัยนี้ไม่ออก |
| **ใช้ Docker แล้วทำไมไม่ใช้ ECS หรือ EKS** | ECS/EKS จัดการ orchestration ให้อัตโนมัติ ทำให้มองไม่เห็นกลไกที่ต้องการศึกษา · EC2 + ALB ทำให้เห็นทุกขั้นตอนตั้งแต่การลงทะเบียนกับ target group ไปจนถึงการถอดเครื่องออกตอน deploy |
| **EC2 สองเครื่องอยู่ AZ เดียวกันได้ไหม** | ไม่ควร ถ้า AZ นั้นล่มระบบดับทั้งหมด ระบบนี้บังคับให้เครื่องกระจายตาม subnet ที่อยู่คนละ AZ ตั้งแต่ในโค้ด Terraform |
| **ถ้า EC2 ล่มทั้งสองเครื่องจะเป็นอย่างไร** | ระบบหยุดให้บริการ เป็นข้อจำกัดที่ยอมรับตามขอบเขตโครงงาน และระบุไว้ในหัวข้อข้อจำกัดแล้ว ทางแก้คือ Auto Scaling Group |
| **Rollback ทำงานอย่างไร** | ECR เก็บ image ทุกเวอร์ชันโดยแท็กด้วย git SHA เมื่อต้องย้อนกลับ ให้เรียก workflow rollback พร้อมระบุแท็ก ระบบตรวจว่ามี image นั้นจริงก่อน แล้ว SSM สั่งทุกเครื่องดึงมารันทีละเครื่อง ใช้เวลาไม่กี่นาทีเพราะไม่ต้อง build ใหม่ |
| **Deploy แล้วผู้ใช้ที่กำลังใช้งานอยู่จะเป็นอย่างไร** | ไม่ได้รับผลกระทบ เพราะ deploy ทีละเครื่องและ ALB ตั้ง `deregistration_delay = 30` วินาที ให้คำขอที่ค้างอยู่ทำงานจบก่อน ประกอบกับแอปรองรับ SIGTERM อย่างถูกต้อง |
| **รู้ได้อย่างไรว่า ALB กระจายโหลดจริง** | `/health` คืนชื่อเครื่อง AZ และเวอร์ชันในทุกคำตอบ · หน้า "สถานะระบบ" ตรวจทุก 2 วินาทีแล้วแสดงสัดส่วนคำขอต่อเครื่อง · และมีสคริปต์ `loadtest.sh` ที่ยิง 120 คำขอแล้วนับผลได้ 50/50 |
| **ทำไมต้องใช้ ECR ในเมื่อมี Docker Hub** | (1) อยู่ใน region เดียวกันจึงดึงเร็วกว่าและไม่เสียค่าข้อมูลออกนอก AWS (2) ควบคุมสิทธิ์ด้วย IAM ไม่ต้องเก็บรหัสผ่านบนเครื่อง (3) Docker Hub จำกัดจำนวนครั้งที่ดึงต่อชั่วโมง |
| **ความลับอย่างรหัสผ่านฐานข้อมูลเก็บที่ไหน** | SSM Parameter Store แบบ SecureString ที่เข้ารหัสไว้ EC2 ดึงเองตอน boot ผ่าน IAM role ที่มีสิทธิ์อ่านเฉพาะ path ของโครงงานนี้ · **ไม่มี credential ใดอยู่ในโค้ดหรือใน user-data** เพราะ user-data อ่านได้จาก EC2 Console |
| **ทำไม GitHub Actions ไม่ต้องมี AWS Access Key** | ใช้ OIDC — workflow ขอ token จาก GitHub แล้วแลกเป็น credential ชั่วคราวของ AWS ที่ผูกกับ repository นี้เท่านั้น ถ้ารั่วก็ใช้ไม่ได้เพราะหมดอายุเร็ว |
| **ค่าใช้จ่ายเท่าไหร่** | ประมาณ 66–85 USD ต่อเดือนช่วงพัฒนา และประมาณ 162 USD ต่อเดือนสำหรับ production ที่มี HA เต็มรูปแบบ · ตัวที่กินเงินมากที่สุดคือ ALB และ NAT Gateway ที่คิดเงินตลอดเวลาที่เปิดอยู่ |
